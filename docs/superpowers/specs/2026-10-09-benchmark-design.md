# Large-dataset benchmark — design

Status: **approved 2026-10-09** · Roadmap: Q4 2026 "Published benchmark" · Output: `docs/performance.md` → "Benchmarks"

## Goal

Measure how OpenGridX behaves at 10k, 100k, 500k and 1M rows with a script anyone can rerun. Publish the numbers with the machine they came from. The point is not a headline number; it's a repeatable check that catches performance regressions and states the limits plainly.

## What is measured

| Metric | How | Engines |
| :--- | :--- | :--- |
| **Mount** | Time from `render()` to the first frame with rows painted (`requestAnimationFrame` after `onStateChange`/first commit) | All 3 |
| **Sort** | `apiRef.setSortModel` on a number column, then on a string column, to the next painted frame | All 3 |
| **Filter** | `apiRef.setFilterModel` (string `contains`, number `>`), to the next painted frame | All 3 |
| **Quick filter** | One quick-filter term over all columns | All 3 |
| **Group + aggregate** | `setRowGroupingModel(['region'])` with a `sum` aggregation, to the next painted frame | All 3 |
| **Scroll** | 5 s scripted scroll (constant velocity, then jumps to random offsets) inside the scrollable range. Frame times from `requestAnimationFrame`: p50, p95, p99, % of frames over 16.7 ms and over 33 ms | All 3 |
| **Long tasks** | `PerformanceObserver('longtask')` during scroll and sort | Chromium only (other engines lack the API) |
| **Memory** | Heap after mount minus a baseline with the same row data and no grid (`performance.measureUserAgentSpecificMemory` or CDP `Runtime.getHeapUsage`) | Chromium only |
| **DOM size** | Rendered `[role="row"]` and cell count after scrolling: shows virtualization is working | All 3 |
| **Reach** | The furthest row index that can be scrolled into view, compared with the row count. Reports the browser height ceiling instead of hiding it | All 3 |

Each measurement is repeated 5 times. The median is reported, with the min–max spread. The first run is discarded as warm-up.

## Setup

- **The app is the built package, not `lib/`.** A Vite app in `bench/app` installs the packed tarball, like the smoke fixtures, so the numbers reflect what users get. It is built in production mode, so React development checks don't distort timings.
- **Data:**
  - **Rows:** deterministic, generated by a seeded PRNG in the page, not counted in any timing.
  - **Columns:** 12 columns of mixed types: id, string, number ×4, date, boolean, singleSelect and others.
  - **Formatting:** `valueFormatter` on 2 numbers.
  - **Layout:** 2 pinned columns.
- **Row heights:**
  - The default 52 px for 10k, 100k and 500k.
  - For 1M, the benchmark runs at 52 px (and reports the reach ceiling) **and** at 32 px (compact), which Chromium can fully scroll.
- **Grid size:** the page is 1280×800, and the grid fills it.
- **Runner:**
  - `bench/run.mjs` packs the library, builds the app and drives it with Playwright.
  - Each row count runs in a new page, so earlier runs don't skew memory.
  - It writes `bench/results/<YYYY-MM-DD>-<machine>.json`, including CPU, cores, RAM, OS, browser versions and the package version.
- **Command:** `npm run bench`.
  - `-- --rows 100000,1000000` and `-- --engine chromium` narrow the run.
  - `-- --quick` does 1 repeat and skips 500k, for local checks.
- **Report:** `bench/report.mjs` turns a results file into the Markdown tables in `docs/performance.md`, with the machine noted above them.

## Not in scope

- **Comparisons with other grids:** a fair cross-library benchmark needs the same data, columns and features in each grid and careful review. It may come later, as its own page.
- **CI gating:** shared CI machines are too noisy for timing thresholds. A weekly `bench` job runs Chromium `--quick` and uploads the JSON as an artifact so trends are visible; it never fails the build on numbers.

## Definition of done

- `npm run bench` runs end to end on macOS, and on Linux in CI with `--quick`.
- `docs/performance.md` has a "Benchmarks" section: method, machine, tables per row count, the reach ceiling explained, and how to rerun.
- A short wiki-visible note in `docs/features/virtualization.md` links to it.
- Lint, typecheck and the existing test gates are unaffected. The bench files are outside `lib/`, outside the npm package, and excluded from the unit and browser projects.
